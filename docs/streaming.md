# 流式响应排错

流式请求“能返回但中途断掉”时，先把问题拆成连接、解析和服务端三层。

## 客户端必须记录

- 首包时间（TTFT）；
- 最后一个事件时间；
- 收到的事件数量；
- 最后一个可解析的 `delta`；
- 是否收到结束标记；
- HTTP 状态码、模型名和请求 ID。

不要只记录最终拼接出的文本，因为中途断开时最终文本可能是不完整的。

## 常见原因

| 现象 | 优先检查 |
|---|---|
| 首包前超时 | Base URL、网络、代理和服务端排队 |
| 有内容后突然断开 | 读取超时、反向代理 idle timeout、客户端取消 |
| 文本正常但工具调用坏掉 | `tool_calls` 分片拼接逻辑和 JSON 缓冲 |
| 最后没有完整结果 | 是否正确处理结束事件和 `finish_reason` |
| 重连后账单变高 | 是否把已完成请求再次无条件提交 |

## 重试原则

1. 为每个业务任务生成稳定的 `task_id`；
2. 记录已经收到的内容和 usage；
3. 只有确认请求没有完成，才进入重试；
4. 重试使用退避，不要固定间隔猛发；
5. 重试后对照服务端用量，确认是否发生重复计费。

本仓库的报告工具只能根据本地 JSONL 发现“短时间内同一任务重复调用”的迹象，不能替代服务端账单核验。

## 不要假设缓存命中

流式输出、上下文长度、请求前缀和时间间隔变化，都可能影响实际计费。记录每次 `prompt_tokens` 与 `completion_tokens`，不要在文档里承诺固定缓存命中率。
